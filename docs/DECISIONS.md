# Decision log

- **Benchmark repo:** The assignment's taubench.com link goes to tau³-bench (`sierra-research/tau2-bench`), not the older `tau-bench` repo. The old repo's README says it's outdated. It matters because only tau2-bench has the voice/audio mode, the half-duplex agent API (`HalfDuplexAgent`) and the evaluator used here. Pinned at commit `b7ea907`; the local airline run's results.json reports the same `git_commit`.
- **STT/TTS architecture:** A LiveKit `Agent`/`AgentSession` (cascaded STT→LLM→TTS, each piece swappable in config) is wrapped as a tau2 half-duplex agent, and its tool calls are routed back through tau2's orchestrator so tau2 grades the DB and actions. I did not use tau2's built-in audio-native mode. Its realtime providers have no separate STT/TTS slot. tau2 also ships a cascaded `--audio-native-provider livekit`, but it calls `livekit.plugins` directly rather than `Agent`/`AgentSession`, and it runs full-duplex with a voice user simulator, which costs more.
- **Plugin registration bug and fix:** LiveKit raises `RuntimeError: Plugins must be registered on the main thread` if a plugin is first imported on a worker thread. `bridge.py` builds STT/LLM/TTS on its own thread. tau2 only pre-registers plugins for `VoiceRunConfig` with provider `livekit`, so our `TextRunConfig` path never got it. The fix has two parts in `cli.run()`, both before `run_domain()`: (1) call tau2's `preregister_livekit_plugins()`, which in our env still registers openai and deepgram even though it logs "Failed to pre-register" (anthropic and elevenlabs aren't installed); (2) call `_preimport_configured_plugins(cfg)`, which imports whichever providers the config names (anthropic, google, cartesia), since (1) never reaches them. Verified: building the LLM on a worker thread fails without the fix and works with it.
- **Test gap:** The offline tests inject `ScriptedLLM` through `_llm_override`, so `build_llm()` never runs and the plugin bug stayed hidden while all 4 tests passed. The fix was checked with a one-off script that runs the real `build_llm/build_stt/build_tts` on a worker thread with dummy keys, but that check is not yet a test in `tests/`.
- **Concurrency / rate limits:** In the local `tau2 run` (airline, gpt-4o as both agent and user simulator), task 1 ended as `infrastructure_error`. The cause was `openai.RateLimitError` 429: gpt-4o at 30,000 tokens per minute (TPM), with 30,000 used and 525 requested. It was raised in the user simulator's `generate()`, and tau2's retry wrapper (tenacity) gave up and re-raised. Mitigations: lower `--max-concurrency` (the concurrency used in that run isn't recorded in the file), use `gpt-4.1-mini` as the user simulator (the scaffold's default), and rerun only the failed task with `--task-ids`.
- **wide30 / retry8 results merge:** `wide30` (test tasks 0–29, `--max-concurrency 1`) ended with tasks 1–8 as `infrastructure_error` (see the next entry). They were re-run as their own run, `retry8`, whose config matches wide30 except for `name` and `task_ids`; all 8 finished `user_stop`. The results went to a separate file because `voice-tau run` names its output after the config's `name` (`results/<name>/`, and tau2's `save_to=<name>` → `vendor/tau2-bench/data/simulations/<name>/`), and neither our CLI nor that call adds to or resumes an existing run. To reconcile, the 8 failed simulations in `results/wide30/results.json` were replaced with the `retry8` ones. Verified: tasks 1–8 now carry retry8's simulation IDs, the other 22 match the original run, and task order and run metadata are unchanged. tau2's copy at `vendor/.../simulations/wide30/results.json` is still the original. Average reward goes from 0.50 to 0.60, because the 0.50 scored the 8 infrastructure errors as 0. `results/wide30/summary.json` predates the merge and still shows 0.50; regenerate it with `voice-tau report results/wide30/results.json` before quoting numbers. Caveat: the retried tasks ran about 25 minutes later, so wide30 now combines two runs of a non-deterministic user simulator.
- **Internet outage vs. rate limits:** In `wide30`, tasks 1–8 each failed immediately (duration 0.0 s, one every ~16 s from 19:32:59 to 19:34:51 IST) with `litellm.InternalServerError: OpenAIException - Connection error.` after 4 attempts, raised in the user simulator's `generate()` (`user_simulator.py:235` → `llm_utils.py`). Task 0 before the window and task 9 onward completed normally. The error itself separates this from the rate-limit failures. Those are HTTP 429 `rate_limit_exceeded` errors that report a tokens-per-minute (TPM) limit and how much of it was used: 30,000 TPM on gpt-4o in the airline run, and 200,000 TPM on gpt-4.1-mini in `baseline` at `--max-concurrency 4`, where 9 of 15 tasks failed. They hit both the user simulator (litellm `RateLimitError`) and the agent (LiveKit's "failed to generate LLM completion after 4 attempts (caused by APIStatusError … 429)", surfaced through `bridge.py`), and they come from running tasks concurrently. The outage returned no HTTP status at all, happened in a concurrency-1 run, and filled one continuous ~2-minute window that then recovered on its own. That fits a dropped network connection; the results file can't say whether it was local or on OpenAI's side. So the fix was a plain retry of the affected tasks, not lower concurrency or a different model.
- **`--audio` http session: three attempts.** The audio loop (user TTS → agent STT each turn, agent TTS on replies) runs plugins on the bridge's private asyncio loop, outside a LiveKit job worker. Some of these plugins get their aiohttp session from LiveKit's `http_context`, a contextvar a job worker normally sets. (1) *Original bridge: no `http_context` at all.* The first STT call failed: `baudio1` (task 0) ended as `infrastructure_error` with "failed to recognize speech after 4 attempts (caused by RuntimeError: Attempted to use an http session outside of a job context)", 0 ASR turns and a null `asr_wer_mean`. The LLM turn itself worked because the OpenAI LLM plugin manages its own client. (2) *Per-call `http_context.open()` around the STT/TTS calls in `_hear`/`_speak`.* This fixes turn 1 and breaks turn 2. `deepgram.STT._ensure_session()` stores the session on first use (`if not self._session: self._session = http_session()`), and `open()` closes that session when its block ends, so the next turn reuses a closed session. Reproduced offline with two back-to-back `recognize()` calls: call 1 sent its request, call 2 raised `APIConnectionError … (caused by RuntimeError: Session is closed)`. Deepgram and Cartesia TTS store their session the same way. (3) *Final fix: one session for the bridge's lifetime.* `_astart` enters `http_context.open()` once and saves the context it bound the session in (`contextvars.copy_context()`). `_hear`/`_speak` run their STT/TTS calls inside that saved context (`_in_http_ctx`, i.e. `create_task(..., context=...)`), because each `_lt.run()` starts a new task with a fresh context. `_aclose` exits `open()` in the same context, so the one session is closed once. `_user_turn`/`_tool_results` are unchanged. Evidence: `tests/test_audio_http_session.py` uses fake STT/TTS plugins that handle the session the way Deepgram does and runs 3 audio turns. Against the original bridge it fails with `Attempted to use an http session outside of a job context`. Against the per-call version it fails differently, with `Session is closed` from turn 2. Against the final fix it passes: every turn transcribes and synthesizes, all 3 plugins share one session, and the session is closed after `stop()`. The full suite is 11 passed. Live run with real OpenAI and Deepgram keys: `baudio3` (tasks 0–2, `--audio --max-concurrency 1`) finished 3/3 `user_stop` with 16 ASR turns, `asr_wer_mean` 0.268 and average reward 0.33. Neither earlier version could have produced 16 ASR turns: the original fails on turn 1, the per-call version on turn 2.
